## Design

### D1. Types + business events (additive)
- DocumentType union += `supplier_credit_note` | `customer_credit_request` | `customer_credit_note` (paper kinds). Amendments/cancellations are NOT document types.
- New `ExtractedData.business_event?: 'new_order' | 'order_amendment' | 'order_cancellation' | 'order_hold' | 'order_instruction_update' | null` (order-related messages only; absent elsewhere) + `ExtractedData.order_amendment?: { amendment_type: 'delivery_date_change'|'quantity_change'|'address_change'|'cancellation'|'hold'|'instruction'; referenced_po: string|null; previous_value?: string|null; requested_value?: string|null; note?: string|null; linked_order_document_id?: string|null; link_status: 'linked'|'unresolved'|'ambiguous' }`.
- New `ExtractedData.credit_document?: { credit_reference, original_invoice_reference, po_reference, reason, net_amount, tax_amount, total_amount, currency }` — verbatim strings, signs as printed (never Math.abs), statement-summary pattern.
- New `ExtractedData.financial_effect?: 'reduces_payable' | 'pending_credit_request' | 'reduces_receivable' | null` — stamped deterministically from type (supplier_credit_note→reduces_payable, customer_credit_request→pending_credit_request, customer_credit_note→reduces_receivable).
- New `ExtractedData.contact_person?: string | null`.
- EFFECT_BY_TYPE: all three credit types → 'operational_financial' (they belong to profiles/history; every operational allow-list excludes them by default — verified above). DOC_TYPE_LABEL, routing.ts RULES (`: []` each), DOC_TYPES tiles/folders, search TYPE_WORDS, TypePicker, DocumentFilters, DocumentsTable, InboxView, finch enums/docu-data, review-queue-shared bucketing (credit docs get their own labels), flags.ts exclusions where type-gated.

### D2. Classification + extraction prompts (anthropic.ts, house voice)
- Enum += the three credit types. Guidance: a document titled Credit Note/Credit Memo/Credit Request is NEVER an invoice. Direction decides the side (reuse document-direction evidence): the org RECEIVING credit from a supplier → supplier_credit_note; a CUSTOMER requesting credit from the org → customer_credit_request; a finalized credit the org issued to a customer → customer_credit_note. For credit docs fill `credit_document` (verbatim; keep printed signs; the requested/credited total — e.g. "Total Credit Requested (Inclusive VAT)" — is total_amount; expected-vs-invoiced comparison columns are NOT line amounts).
- Order lane prompt (order-prompt.ts): add `contact_person` to the JSON shape. Rewrite the customer_name bullet: customer_name = the BUSINESS that placed the order, read from (in order) an explicit business name in the subject/document title, PO header buyer/property, a signature business name, the sender's organization; the HUMAN sender/signatory goes in contact_person; when only a person is identifiable, put the person in contact_person and leave customer_name to the best remaining business cue or "". Add amendment awareness: when the body CHANGES an existing PO ("deliver Wednesday not today", "cancel PO…", "add N boxes to PO…", "hold", address change) it is NOT a new order — set no invented lines and describe the change (the deterministic layer will stamp business_event; the model must not fabricate line items for an amendment).
- Requisition column-role guidance (order lane): in requisition-style tables, columns labeled compliance/primary vendor/vendor price are REFERENCE data — never unit_price, never their own lines.

### D3. Deterministic amendment detection + linkage (new pure module lib/platform/docu/order-amendment.ts)
- Deterministic cues (regex, tested): delivery-date-change ("deliver … on <day/date> … (and )?not (today|<day>)", "please change delivery date"), cancellation ("cancel (this|the|po)"), hold, address change, additive quantity ("add N … to (po|order)"), + a referenced PO (reuse PO_NUMBER_PATTERN family). Rule: order-classified message + amendment cue + referenced PO + (zero extracted lines OR explicit change language) → business_event stamped (deterministic override of model output; the suppression tags remain for enquiries/complaints).
- Linkage (READ-ONLY): find org documents where document_type='order' AND extracted_data->>purchase_order_number = referenced_po AND superseded_at is null. Exactly 1 → link_status 'linked' + linked_order_document_id (+ resolve its of_order via source_document_id for display). 0 → 'unresolved'. >1 → 'ambiguous'. NEVER mutate the operational order.
- Routing guard: runDocumentSideEffects order branch returns early (no syncOrderFromDocument) when business_event is amendment/cancellation/hold/instruction — plus a defensive check inside syncOrderFromDocument mirroring its existing type guard. documents_created semantics unchanged (the review doc exists).
- Prerequisite fix (approved): write `customer_po: ed.purchase_order_number ?? null` at the of_orders insert (orderflow-from-doc.ts:792-796) — creation-time only, never mutating existing orders.

### D4. Business-customer vs contact resolution (customer-match.ts, additive)
- CustomerIdentityEvidence += `documentTitle?` and `contactPersonName?`; callers pass subject (already there), filename/title, extracted contact_person.
- New ladder arm between 2 and 3: `exact_name_in_text` conf 97 — a customer/trading name (normalized) appearing as a whole phrase inside subject/documentTitle (bounded body prefix optional) → that customer; collisions → ambiguous. This is how "Scooters Pizza Rosebank Order" resolves deterministically.
- Name pools gain kinds: business names (customer.name, trading_name) vs person names (cd_contacts names, senderName, contactPersonName). Arms 3/5 prefer business-kind matches; a person-name-only match yields the customer via its contact linkage as today but records `matched_via: 'contact_person'`; person evidence NEVER outranks an explicit business-name match. Evidence block now records subject + documentTitle (bounded) so ambiguity is debuggable.
- Branch-token support: when multiple candidates share a domain, a distinctive token from subject/title matching exactly one candidate's name resolves it; "BALLYOAKS" matches none → stays unresolved with candidates listed (the Doppio case; report the alias gap to Josh — do NOT auto-create aliases).
- Fill `customer_name` display: when resolver lands a business customer and extraction had only a person, the review UI shows Customer = resolved business, Contact = contact_person. Extraction values are never overwritten; resolution lives in customer_match_* + customer_id as today.

### D5. Credit routing
- Supplier credit notes: supplier LOOKUP-ONLY (new lookup variant of resolveSupplierProfile that matches existing suppliers/aliases but NEVER creates; unresolved → review, supplier_id null). SupplySync: add `supplier_credit_note: 'credit_note_received'` to HISTORY_EVENT_BY_TYPE + label; EXPLICITLY keep it out of SPEND_DOC_TYPES (test). ProcurePulse/PriceWatch/DocWatch/pricing exclude by allow-list (tests). Hubdoc: read hubdoc-shared eligibility; add explicit type exclusion if it is not type-gated. No ss_supplier_credits auto-creation (manual claims system; future linkage noted).
- Customer credit request/note: resolve customer via resolveExistingCustomerForOrg (read-only) on ALL lanes for these types; set documents.customer_id → they appear on the existing customer profile documents list with zero extra plumbing. NEVER run supplier resolution for customer-side credit docs. No of_credit_notes auto-creation, no AR mutation.
- Part E decision (reported): NO document_party_links table — customer_id/supplier_id + the existing profile surfaces carry everything in scope; entity_type/entity_id first-writer deferred until an operational record exists to link.

### D6. Rotation integrity (pdf-orientation.ts + both lanes)
- New deterministic trigger: when the single page's /Rotate ≠ 0, ALWAYS run the multi-rotation candidate comparison (do not wait for score<70 — Scan B's hallucination scored 81 "ok"). Keep the existing score<70 trigger for unrotated pages. Comment with the Scan B case.
- Rotation-suspect reads (original /Rotate ≠ 0) that were NOT normalized keep the existing adopted-rotation confidence cap semantics and are held for review (existing convention). Multi-page rotated PDFs remain unrecovered — unchanged limitation, restated.
- Statement-lane guard: classification retry uses the same deterministic trigger, so a sideways page can't lock in supplier_statement from a fabricated read without the rotation candidates having been compared.
